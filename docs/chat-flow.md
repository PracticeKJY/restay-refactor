# 채팅 수정 및 확인 사항

## 수정 이유와 범위

- 기존 전송 코드는 성공 후 메시지 상태를 갱신하지 않고 Realtime INSERT에 의존했다. 이제 전송 직후 임시 메시지를 표시하고 기존 `/api/messages/send`의 응답 ID로 확정한다. 응답과 Realtime 도착 순서가 달라도 ID로 중복을 제거한다.
- Supabase 세션 초기화가 잘못 호출하던 GET `/api/messages`를 기존 GET `/api/session/supabase`로 연결했다. 동시에 실행되는 초기화 요청은 공유하고 서버에서 전달한 로그인 이메일과 일치하는지 확인한다. 인증 정책이나 서버 구현은 변경하지 않았다.
- 대화방 UUID와 발신자 이메일을 화면 제목/메시지 라벨에서 제거했다. UUID는 정상적으로 딥링크 URL과 내부 식별자로만 사용한다. 호스트 이름은 기존 숙소 조회 응답에 있을 때 표시하며, 없는 경우 호스트/게스트 역할을 표시한다.
- 데스크톱에서는 목록/대화 2열, 모바일에서는 목록과 대화를 분리한다. 날짜 구분, 말풍선, 전송 상태, 오류 재시도, 한국어 IME 입력을 지원한다.
- 메시지는 최근 50개로 초기화한다. Realtime 외에도 보이는 탭에서 방은 8초, 목록은 30초 간격으로 다시 조회한다. 실제 Realtime이 작동하지 않을 때도 재조회로 복구하지만, 이를 실시간 연결 성공으로 간주하지 않는다.

## 진입 흐름

1. 사용자 메뉴 → 메시지 → 참여 중인 채팅방.
2. 여행 → 예약 카드의 호스트에게 연락하기 → 해당 예약의 기존 방 조회 → 없으면 기존 `/api/chat/get-or-create` 호출 → 채팅방.
3. 여행 데이터에서 숙소 ID와 예약 ID를 분리해 실제 예약 ID를 전달한다.
4. 기존 결제 후 예약/방 생성 및 홈 이동 흐름은 유지한다. 소스에 특정 도메인에서만 메시지를 열도록 하는 제한은 없었다. 단, 기존 서버의 URL 환경설정과 인증 환경은 유효해야 한다.
5. 기존 API의 세션·멤버 검증과 Supabase RLS는 유지한다. 조회 권한 오류를 무시하거나 우회하지 않는다. 기존 방을 다시 열 때 생성 API를 호출하지 않아 upsert의 부작용을 피한다.

## 검증

- Node.js v22.17.0 / Next.js 15.5.9 / Windows PowerShell.
- TypeScript 및 Production Build 통과. 개발 서버와 출력 충돌을 막기 위해 임시 스크립트에서 `.next/chat-verification`에 빌드했다. 프로젝트 설정 파일과 환경변수는 변경하지 않았다.
- ESLint 오류 0개. 기존 `home-client.tsx`의 `setType` 의존성 경고 1개 유지.
- 채팅 단위/모의 Hook 테스트: 즉시 표시, HTTP/Realtime 경쟁, 중복 제거, 초기 조회 병합, 세션 초기화 중복 방지, 전송 API 계약, 기존 방 열기 무변경 검증. 실제 메시지 전송이나 운영 DB 쓰기는 수행하지 않았다.

## 브라우저에서 확인할 항목

- 로그인한 호스트와 게스트를 서로 다른 브라우저에서 열고 양방향 수신, 전송 직후 표시, 새로고침 후 저장 여부 확인.
- 메시지 메뉴 및 여행 카드에서 실제 예약에 대응하는 방으로 진입하는지 확인. 한국어와 `/en` 모두 확인.
- 320/375/768/1024px 및 데스크톱에서 가로 넘침, 대화 스크롤, 모바일 뒤로 가기, 키보드와 입력창 확인.
- Enter 전송, Shift+Enter 줄바꿈, 한국어 조합 중 Enter의 중복 전송 방지 확인.
- 오프라인/실패 상태 표시와 수동 재시도 확인. 요청은 저장됐지만 응답만 유실된 경우 기존 API에 멱등성 키가 없어 수동 재시도 시 중복 저장 가능성이 있다. 쓰기 요청을 자동 재시도하지 않는다.
- 타인 채팅방/로그아웃 상태 접근 차단은 실제 로그인 환경에서 확인. 로컬 Production의 기존 UntrustedHost 설정 문제는 이번에 변경하지 않았다.
- Supabase Realtime publication에 messages가 포함됐는지 및 현재 RLS에서 수신 가능한지는 대시보드/실제 계정으로 확인해야 한다. 정책을 변경하지 않았다. [Supabase 공식 안내](https://supabase.com/docs/guides/realtime/postgres-changes).
- 기존 생성 API가 요구하는 숙소의 `userId`가 없는 예약은 방 생성이 실패할 수 있다. DB 스키마/데이터 보정은 이번 범위에서 수행하지 않았다.
